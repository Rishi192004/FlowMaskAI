===============================================================================
1. PROJECT OVERVIEW
===============================================================================
FlowMind is a process-mining platform for analyzing purchase-to-pay event logs.
It ingests raw events, normalizes them into case/activity/timestamp records,
reconstructs observed workflows, calculates operational metrics, checks process
conformance, and presents evidence-backed recommendations.

The reference P2P flow is:
Purchase Requisition -> Manager Approval -> Purchase Order Created ->
Goods Received -> Invoice Received -> Invoice Verified -> Payment Completed

The repository includes a synthetic P2P sample with more than 100,000 events.
This sample supports repeatable development and testing; it is not evidence of
production customer outcomes.

INTERVIEW-READY PROJECT STORY
-------------------------------------------------------------------------------
60-90 second answer:
"I built FlowMind, a purchase-to-pay process-mining platform that turns
inconsistent event logs into measurable workflow insights. The ingestion
pipeline maps source columns, normalizes timestamps, checks data quality,
deduplicates events, and stores case-activity-time records. I then use SQL and
PM4Py to analyze cycle time, activity delays, rework, process variants, SLA
breaches, and conformance against a reference process. FastAPI exposes those
computed results, while a configurable rules engine produces evidence-backed
recommendations. For natural-language questions, the assistant routes a fixed
intent to existing analytics services and uses local Ollama only to phrase an
answer from structured evidence. Metrics stay server-computed; the model has no
SQL access. The sample data is synthetic, so I describe the result as a working,
tested analytics workflow rather than claiming production savings."

STAR framing:
- Situation: P2P event exports can have inconsistent columns, duplicate events,
  missing values, and timestamps that do not reflect a valid event order.
- Task: Build a repeatable path from raw events to process analysis and
  recommendations that users can inspect.
- Action: Implement CSV ingestion and quality checks, case-level analytics,
  PM4Py discovery/conformance, typed FastAPI endpoints, configurable rules,
  and a locally hosted natural-language interface.
- Result: The platform turns event records into analysis-ready logs and
  traceable metrics/recommendations. Do not claim a measured reduction in
  processing time, cost, or risk; this repository does not establish such an
  outcome.

Concrete ETL example from the attached small CSV:
- It contains a blank activity, a repeated event row, and an approval timestamp
  earlier than the preceding requisition event. Use these as examples of data
  quality checks, not as a basis for KPI claims. The sample is too small and
  incomplete to infer SLA performance, abandonment, or business impact.

Likely follow-up answers:
- "How do you prevent AI hallucinations?" Intent classification selects fixed
  service calls; metrics and recommendations are serialized as evidence; the
  model has no database/SQL tool; its narrative is kept separate and numeric
  claims are rejected. Unsupported questions return an explicit unavailable
  response.
- "How do you calculate first-pass yield?" It is based on case-level
  conformance and repeated-activity records, rather than combining aggregate
  percentages.
- "What is the main limitation?" The sample is synthetic, the full backend
  suite has existing environment/fixture failures, and live Docker end-to-end

===============================================================================
3. IMPLEMENTED CAPABILITIES
===============================================================================

Application foundation
- FastAPI application, API versioning, structured logging, CORS, and health check.
- JWT registration, login, refresh, and current-user flows.
- Project and dataset lifecycle endpoints.
- SQLAlchemy models and Alembic migration support.

Event ingestion and ETL
- CSV delimiter detection and source-column synonym mapping.
- Timestamp normalization and activity-name preservation.
- Validation for missing data, duplicate event signatures, and out-of-order
  timestamps.
- Chunked database loading with ETL execution and data-quality records.
- Synthetic P2P event log with standard and deviating process variants.

Operational analytics
- Case, event, completion, and incomplete-case counts.
- Cycle-time measurements and percentiles.
- Activity waiting-time calculations and bottleneck rankings.
- Repeated-activity/rework counts and rates.
- SLA breach measurements using a configurable cycle-time target.
- Vendor and department summaries, including spend and performance metrics
  when those attributes exist in the source data.

Process mining and conformance
- Conversion of stored events to PM4Py event-log and dataframe formats.
- Directly-Follows Graph discovery and transition timing.
- Inductive Miner Petri-net discovery with a structural fallback.
- Variant discovery, frequency/Pareto analysis, outlier detection, and
  comparison across supported dataset dimensions.
- Configurable reference-flow conformance checks for skipped approval,
  early invoice verification, skipped invoice verification, repeated approval,
  incomplete cases, out-of-order activities, and unexpected activities.
- Case-level evidence and a token-replay fitness approximation.

Grounded recommendations
- Eight independently evaluated rules: SKIP_APPROVAL, EARLY_INVOICE,
  SKIP_VERIFICATION, HIGH_REWORK, APPROVAL_BOTTLENECK, LOW_FPY,
  HIGH_ABANDONMENT, and SLA_BREACH.
- Rule thresholds are configurable through the recommendations API.
- Recommendation evidence, metric values, threshold comparisons, case counts,
  corrective actions, severity, and ranking scores are returned in a typed
  response.
- First-pass yield is computed from conformant case records with no repeated
  activities; it is not estimated by combining aggregate rates.
- Bottleneck case counts use distinct cases, not transition counts.
- Cases without a payment event are reported as incomplete; the event log alone
  cannot establish that they were abandoned or are still active.
- Impact descriptions use observed counts and timings. The engine does not
  claim unmeasured savings or fabricate financial outcomes.

Frontend
- Ten React/TypeScript pages: overview, dataset management, ETL, data quality,
  process discovery, variants, conformance, bottlenecks, vendor performance,
  and the AI Process Assistant.
- Analytics visualizations, process views, and recommendation feed are
  connected to backend data.

AI Process Assistant (Phase 3)
- POST /api/v1/ai/assistant/query classifies supported questions into fixed
  intents and routes them to existing analytics or conformance services.
- Supports bottleneck, vendor SLA, cycle-time, rework, reference-process
  conformance, and management-priority questions.
- Management-priority questions use the configurable recommendation engine.
- Uses local Ollama generation configured with OLLAMA_HOST and OLLAMA_MODEL
  (default model: qwen3:8b). No external LLM provider is used.
- Computed facts, configured baselines, and recommendation records are returned
  separately from the generated narrative. Narrative numeric claims are
  rejected; unsupported intents and unavailable data receive explicit responses.
- The LLM has no SQL or database tool access. Intent handlers call fixed
  analytics services; user text is never converted into SQL.
- The React assistant now sends queries to this API and renders measured facts
  separately from recommendation-engine actions.
